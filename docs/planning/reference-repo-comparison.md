> ① [johnainana/product-manager-workflow](https://github.com/johnainana/product-manager-workflow)（已读：SKILL.md 全文、references/templates.md 全文、README）
> ② [dontbesilent2025/dbskill](https://github.com/dontbesilent2025/dbskill)（已读：dbs 路由器、dbs-save、dbs-diagnosis 全文、30 个 skill 目录、README）

## 0. 摘要

三个仓库代表 skill 系统的三种形态：①是**单 skill 深工艺**（一个 400 行 SKILL.md + 懒加载模板库，把访谈纪律做到极致）；②是**人格化工具箱生态**（30 个 skill + 知识库 + 存档系统，把"系统会跟进"做到极致）；Oh-My-PM 是**工程化工作流**（12 skill + 契约/测试/评估体系，把可验证性做到极致）。

核心结论：**设计哲学三家已趋同（澄清先行、证据纪律、动态路由），Oh-My-PM 在工程化（测试、契约、防幻觉）上独家领先，但在访谈工艺细节（①）和任务后导航与决策存档（②）上仍有 10 项可吸收的增量。**

## 1. 三仓库总览

| 维度 | Oh-My-PM (v1.1.0) | ① product-manager-workflow | ② dbskill |
|:--|:--|:--|:--|
| 定位 | PM 全流程工作流系统 | PM 访谈→交付物单一工作流 | 创业者/创作者商业工具箱 |
| 规模 | 12 skills + 6 subagents + 4 commands | 1 个 skill（+单文件变体） | 30 个 skill + 知识库 + 推文集 |
| 核心抽象 | 三层主线+验证辅助、Plan-and-Execute | 9 阶段访谈 → 10 交付物 | /dbs 三模式路由 + 存档 |
| 状态持久化 | `.ompm/*.json` 工作流状态 + memory 文件约定 | 无（单对话内完成） | `~/.dbs/` 存档系统（save/restore/report） |
| 质量保障 | 结构测试 15 项 + 行为 evals 16 案 + JSON Schema 契约 | 无 | 无（有 build 脚本和 beta 隔离） |
| 分发 | npx skills（70+ agent）+ Claude marketplace | 文件夹上传 / 单 md 上传 | npx skills + Claude marketplace + 多端桥接 |
| 语言 | 中文为主 + 英文触发后缀 | 跟随用户语言 | 中文为主，description 中英双语 |

## 2. 与 ① 的逐项对比

### 已吸收（v1.0.0 落地）

| ①的设计 | Oh-My-PM 落点 |
|:--|:--|
| 缺失信息标【待确认】、无证据标【未验证】 | 证据纪律内联 5 个产出型 skill |
| 输出前信息完整度检查 | clarify-requirements Step 5/6、prd-gen 完整度检查门 |
| 一次只问一个问题 | clarify-requirements、prd-gen Step 0.5 |
| 9 步访谈主线 | full-pm-cycle 各阶段"必答问题" |
| 评审 Checklist | prd-gen 预审尾门（三视角挑战） |
| A/B 验证方案 | retrospective 输出模板 |

### 差距（未吸收，按价值排序）

| # | ①的做法 | 我们的现状 | 价值 |
|:--|:--|:--|:--|
| 1 | **阶段进度显式化**：提问带 `当前阶段：1/9 背景与触发原因` | 澄清过程无进度指示 | 高：用户知道还要被问多久，放弃率降低 |
| 2 | **按交付物就绪度分别生成**：完整度检查含"可生成的输出物"表（每项交付物标 可生成/原因），不就绪的不硬凑 | 完整度门是全有/全无 | 高：部分就绪时不再卡住整个流程 |
| 3 | **不复读用户回答**：默认不逐条复述，仅含糊/矛盾/影响后续时复述确认 | 无此约束，模型爱鹦鹉学舌 | 中：对话节奏显著加快 |
| 4 | **可审计性**："每个产出都能追溯到已确认输入、引用证据或用户显式决策" | 证据纪律只管标记，无追溯链表述 | 中：一句话规则，评审时价值大 |
| 5 | **优先级方法按上下文选择并说明理由**（RICE/MoSCoW/Kano/value-cost/impact-effort） | product-strategy 写死 RICE/MoSCoW | 中：小团队/探索期项目 RICE 并不合适 |
| 6 | **多交付物先出目录再逐个生成** | 无 | 低：顺手 |
| 7 | **模板懒加载**：SKILL.md 只写规则，`references/templates.md` 写模板，生成时才加载 | 模板全内联（prd-gen 647 行） | 中：省主对话上下文（P2 方向） |
| 8 | **外部事实不查就标【未验证】**（定价/法规/API 能力），默认不联网 | 防幻觉规则是搜索先行（perception） | 低：定位不同——prd-gen 可借鉴此姿态 |

### ①不如我们的地方

- 无任何测试/契约机制，skill 改动无回归保障（我们有结构测试 + 行为 evals + JSON Schema）
- 无防幻觉规则（它靠"不联网"规避，我们靠"搜索先行+来源必注"正面解决）
- 单对话完成一切，无跨会话状态（我们有 `.ompm` 状态 + 记忆约定）
- PRD 模板 20 章一刀切（我们有三场景 + 章节选择 + 预审尾门）
- 无路由概念（单 skill 不需要，但也无法扩展）

## 3. 与 ② 的逐项对比

### 已吸收（v1.0.0/v1.1.0 落地）

| ②的设计 | Oh-My-PM 落点 |
|:--|:--|
| 单入口调度，用户不需知道该调谁 | ompm skill（全局意图路由） |
| 读上下文+状态判断"最有价值下一步" | ompm 意图路由（读 current-workflow.json） |
| 按用户目标组织能力图（不按内部架构罗列） | ompm help 能力图 |
| 存档/状态跨会话延续 | `.ompm/current-workflow.json` + workflow-state 快照 |
| 能力图入口中英文混排、触发词宽泛 | ompm description + 全量英文触发后缀 |

### 差距（未吸收，按价值排序）

| # | ②的做法 | 我们的现状 | 价值 |
|:--|:--|:--|:--|
| 1 | **任务后导航地图**：每个 skill 一张"结论信号→下一步"表（如"诊断出做不动→dbs-action"），基于**产出内容**而非状态路由 | ompm 只有事前路由，无事后导航 | **最高**：这是"系统会跟进"和"系统只应答"的分水岭 |
| 2 | **存档记录"已否决的方向"**：dbs-save 格式含 `用户已否决的方向（附理由）` + `待验证假设` | 状态文件只记"做了什么"，不记"决定不做什么" | 高：避免二次讨论重走已否决路径 |
| 3 | **跨 skill 交接契约**：禁止 skill 预设下一站（禁用"路由到/建议用"措辞），完成后统一交回 `/dbs` + 标准收尾块 | skill 间用 output-to 静态路由，无收尾标准 | 中高：让 ompm 成为真正的枢纽而非摆设 |
| 4 | **新手教程模式**（`/dbs 新手入门`：教程→立即完成首次真实使用） | ompm 只有 help 能力图 | 中：降低首次使用门槛 |
| 5 | **边界情况规则**：多需求→"先解决哪个"；超范围→明示能力清单；闲聊→拒接 | ompm 无边界规则 | 中：几行的事 |
| 6 | **存档格式工程化**：slug 项目隔离、位置三模式（default/project/custom）、隐私提醒、list 模式、一行回执、next_skill"错了比空更糟" | 状态文件单点、无项目隔离、无位置配置 | 中：多产品并行的用户才需要 |
| 7 | **说话风格规则**（"不解释价值""不加感叹号""回执只一行"） | 各 skill 无统一语气规则 | 低：风格统一性 |
| 8 | **消解漏斗思维**（dbs-diagnosis：语言陷阱→假设错误→逻辑错误→事实核查→信息充分性，逐层对话式过滤） | clarify-requirements 是"补齐信息"导向，没有"问题本身可能不成立"的消解视角 | 中：哲学层补充——澄清的不只是信息，还有问题本身 |

### ②不如我们的地方

- 无测试无契约（30 个 skill 靠人工维护，曾有"核心业务 skill 无法独立运行"的 bug——v2.18.14 才修，正是我们 contracts 防的那类问题）
- skill 间导航地图靠手工维护在路由器里，30 个 skill 的导航表已经很长，扩展性是隐患
- 内容强领域绑定（dontbesilent 个人方法论+知识原子库），通用性弱
- 无模型分级/执行画像概念（我们有 Execution Profile + subagent 隔离）

## 4. Oh-My-PM 独家优势（两家都没有）

1. **行为级 evals**：16 案对抗性用例（含门控绕过测试），已抓获 3 个真实缺陷——这是" prompt 工程"和"prompt 产品"的分界线
2. **可执行契约**：JSON Schema + stdlib 校验器 + 运行期自检 + frontmatter 声明合法性静态检查
3. **防幻觉规则体系**：搜索先行、来源必注、置信度分级、Unknown 合法（①靠回避、②靠人格信誉，我们靠机制）
4. **Execution Profile**：模型分级/工具姿态/记忆文件的跨宿主契约
5. **HTML 原型模板库**（三档保真度 + 组件库 + 质量标准）
6. **双安装通道 + 双语言轨**（npx skills 通用 + marketplace 增强；中文触发 + 英文后缀）

## 6. 风险与注意

- **导航地图的维护成本**：②的 30 skill 导航表已现臃肿，我们 12 skill 可控，但要在 AGENTS.md 立规矩"新增 skill 必须同步 ompm 导航地图"
- **不要吸收 ②的人格化风格**（公理、金句、刺痛式表达）——那是 dontbesilent 的个人 IP，对 PM 工具不适用
- **"消解"思维适量即可**：PM 场景的问题多数成立，消解漏斗作为 clarify-requirements 的一个前置检查即可，不宜做成主流程
