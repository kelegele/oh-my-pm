# AGENTS.md

This file provides guidance to Claude Code and Codex when working with code in this repository.

`CLAUDE.md` in the repo root is a **symlink to this file** — edit `AGENTS.md` only; both entry points stay in sync automatically.

## Overview

Oh-My-PM is an AI Agent workflow system for Product Managers, implemented as a **Skills plugin** installable into Claude Code and Codex. There is no application code, build step, or runtime of its own — the repository is a curated set of Markdown prompt definitions (Skills, Subagents, Commands), HTML prototype templates, and one bash test script.

The system features a **3-layer core (Perception → Strategy → Design) + Validation loop** with **12 Skills** (8 domain + 4 workflows, incl. the `ompm` intent router), **6 Subagents**, and **4 Commands**. The former Delivery layer was retired in v1.0.0: PRD pre-review lives in prd-gen's tail gate, release checklists/strategy live in feature-launch.

**Portability (v1.1.0+)**: the `skills/` layer is self-sufficient — `npx skills add` (any agent: codex, cursor, copilot…) installs all 12 skills with full capability (routing, evidence discipline, execution profiles included). The Claude Code marketplace plugin adds host-specific enhancements on top: 6 subagents (isolated execution, model tiering) and 4 slash commands (quick entry, incl. the `/ompm` shim). Skill bodies must not hard-code host-specific tool names (e.g. `AskUserQuestion`, `mcp__*`) except inside "e.g. on Claude Code…" example phrasing.

Current plugin version: **1.2.0** (see `.claude-plugin/plugin.json` — the single version source). See `docs/planning/roadmap.md` and `CHANGELOG.md` for version history.

## Commands

```bash
# Run skill structure + contract tests (fast, no model calls)
bash tests/test-skills.sh

# Run behavioral evals (real model calls, costs tokens; optionally filter by skill)
bash evals/run-evals.sh [skill-name]

# Install plugin from GitHub
npx skills add kelegele/oh-my-pm -a claude-code   # Claude Code
npx skills add kelegele/oh-my-pm -a codex          # Codex

# Install plugin from a local checkout
npx skills add . -a claude-code
npx skills add . -a codex

# Usage examples (via natural language in Claude Code or Codex)
# "Analyze the competitive differences between Notion and Feishu docs"  → competitive-analysis
# "Write a PRD for user profile redesign"                                → prd-gen
# "How did this feature perform after launch?"                           → retrospective
```

Installing with `npx skills add .` copies the skills into `.agents/skills/` and regenerates `skills-lock.json` / `.plugins-cache.json`. **`.agents/` and `.plugins-cache.json` are git-ignored local install artifacts — never edit them; always edit the source under `skills/`.** `skills-lock.json` is tracked and regenerated by the installer.

## Architecture Overview

### 3-Layer Core + Validation Loop

```

│    .ompm/market-analysis.json, ...              │
└─────────────────────────────────────────────────┘
                       ↓ docs/product/
┌─────────────────────────────────────────────────┐
│  Strategy (策略规划)                             │
│  product-strategy (定位→优先级→路线图)           │
│  → Output: positioning.md, roadmap.md,          │
│    .ompm/prioritization.json                    │
└─────────────────────────────────────────────────┘
                       ↓ docs/product/
┌─────────────────────────────────────────────────┐
│  Design (方案设计)                               │

                       ↓ docs/product/
┌─────────────────────────────────────────────────┐
│  Validation loop (验证辅助，喂数据驱动)          │

```

(Delivery was folded away in v1.0.0: PRD pre-review → prd-gen tail gate; release checklist & rollout strategy → feature-launch.)

### Skills + Subagents Hybrid Model

| Component | Count | Purpose |
|:----------|:------|:--------|
| **Skills** | 12 | Prompt injection for workflow triggering |
| **Subagents** | 6 | Isolated execution with optimized models |
| **Commands** | 4 | Direct CLI invocation |

**Key Difference**: Skills share main conversation context; Subagents run in isolation with custom model selection (haiku/sonnet/opus) and persistent memory.

**Division of labor (v0.10.0+)**: when a domain has both a Skill and a Subagent, the **Skill stays thin** (trigger conditions, input parameters, output contract — JSON schema + quality standards — and stage gates) while the **Subagent carries the depth** (execution methodology, analysis frameworks, detailed procedures). Reference pair: `skills/competitive-analysis/SKILL.md` ↔ `agents/perception/competitive-analyst.md`. Domains that need no model/tool isolation should be Skill-only; new components must follow this split. Since v1.1.0, such skills also carry an `## Execution Profile` section (model tier, tool posture, memory file) — that profile is the cross-host contract, and `agents/*.md` frontmatter is its Claude Code realization; **change one, change the other**.

### Context Passing

Machine-readable intermediate outputs use the **flat `.ompm/<name>.json` model** (unified in v0.9.3) under `docs/product/.ompm/`; human-readable documents sit alongside in `docs/product/`. All paths are workspace-relative — when the plugin is installed into a user's project, outputs land in that project's `docs/product/`. In this repo, `docs/product/.ompm/` is git-ignored runtime state; the few committed files under `docs/product/` are historical samples, not fixtures.

**Contract guard**: the retired legacy filenames (`personas.json`, `user-personas.json`, `market-data.json`, `market_data.json`, `impact.json`, `feedback.json`, `workflow_tracking.json`) must not be referenced anywhere under `skills/`, `agents/`, or `.claude-plugin/` — `tests/test-skills.sh` fails the build if they reappear. (`docs/`, `AGENTS.md`, `README.md`, `CHANGELOG.md` may mention them in historical notes and are not scanned.)

**Contract schemas**: the 9 `.ompm/*.json` context files have executable lightweight JSON Schemas in `contracts/<name>.schema.json` (top-level `required` + `type` only, fields sourced from each skill's declared output structure) with minimal valid examples in `contracts/examples/`. `tests/validate_contracts.py` (stdlib-only) checks every example against its schema; `bin/validate-context.sh <json-file>` validates a runtime output against the schema matched by its basename. When a skill changes its declared `.ompm` output structure, update the matching schema and example.

### Shared Rules & Templates

- **Anti-Hallucination Rules**: Inlined into the search-driven Perception Skills (competitive-analysis, market-research) for standalone installability.
- **Evidence Discipline (证据纪律, v1.0.0+)**: inlined verbatim into deliverable-producing skills (clarify-requirements, market-research, product-strategy, prd-gen, retrospective): missing info → 【待确认】, assertions without evidence → 【未验证】, and a completeness-check gate before formal output. Distinct from anti-hallucination rules (those govern external facts; this governs user input and requirement assertions).
- **`templates/prototype/`**: HTML prototype templates (`wireframe.html`, `mockup.html`, `interactive.html`) plus a component library (`COMPONENTS.md`) and quality standards (`QUALITY-STANDARDS.md`).

## Workflows

### Plan-and-Execute Pattern

All workflows follow the **Plan-and-Execute pattern** with:
- **Stage gates**: Quality criteria before moving to next stage (S0 Setup → S1 Perception → S2 Strategy → S3 Design → S4 Delivery → S5 Validation)
- **State tracking**: `docs/product/.ompm/current-workflow.json`
- **Hard gates**: the Strategy Confirmation Gate (defined in full-pm-cycle's `## Execution Modes`) requires explicit user approval before entering Design — mandatory in `mode: quick` (i.e. quick-prd), default-on in full mode

| Workflow | Command | Description |
|:---------|:--------|:------------|
| **quick-prd** | `/quick-prd "desc" [competitors...]` | Thin preset of full-pm-cycle (`mode: quick`): competitive analysis + PRD |
| **full-pm-cycle** | `/full-pm-cycle "product"` | Complete 0-1 product lifecycle (canonical stage definitions) |
| **feature-launch** | `/feature-launch "feature"` | Feature launch coordination |

The 4th command, **`ompm`**, is a thin shim that activates the **`ompm` skill** — the **global intent router** (routing logic lives in `skills/ompm/SKILL.md`, the canonical source). Routing chain: `help/?` → direct workflow dispatch (`/ompm quick-prd "用户改版" 淘宝 京东`) → **post-task navigation** (when the conversation already contains a skill's output, route by its conclusion signal via the navigation map) → general intent routing (reads `docs/product/.ompm/current-workflow.json` + conversation context) → empty-dialog guidance. The bare `/quick-prd` etc. are shorthand.

**Maintenance rule (v1.2.0+)**: adding or removing a skill requires syncing the `ompm` skill's navigation map and capability map in the same change.

Skills themselves do **not** support `/skill-name` explicit invocation — they trigger through natural language or workflows.

## Subagent Memory System

Each subagent maintains independent memory in `.claude/agent-memory/<name>/MEMORY.md`:

- **market-researcher**: Market data & trends
- **competitive-analyst**: Competitor knowledge base
- **user-interviewer**: User research patterns
- **impact-analyst**: Impact analysis frameworks
- **feedback-collector**: Feedback theme patterns
- **pm-orchestrator**: Workflow best practices

Memory enables cross-session learning without polluting main conversation context.

## Development

### Content Conventions

- Skill and agent definitions are **prompt documents, not code**: write them as instructions to the executing agent. YAML frontmatter keys stay in English.
- **Language policy (dual-track, v1.1.0+)**: `description` fields are user-facing triggers — Chinese-first (our users) **plus an `Also triggers on: …` English phrase suffix** for international routing. Bodies mix Chinese and English: prose follows the user's language (Chinese), while structural tokens (frontmatter keys, layer names, stage IDs, filenames, framework names like RICE/HARD GATE) stay in English and must match across files verbatim. `README.md` (English) and `README-CN.md` (Chinese) are maintained as a synced pair with cross-links; `docs/` is Chinese-first.
- Every `skills/<name>/SKILL.md` starts with YAML frontmatter. Required fields: `name` (must equal the directory name), `description` (includes natural-language trigger phrases), `layer` (one of `perception`, `strategy`, `design`, `delivery`, `validation`, `workflow`). Workflow skills additionally declare `input-from` / `output-to` for context routing. **SKILL.md files do not carry a `version` field** — plugin.json is the only version source (see Versioning & Commits).
- Each skill must be **standalone-installable**: inline any shared rules it needs instead of referencing files outside its directory. Skill bodies must not hard-code host-specific tool names (e.g. `AskUserQuestion`, `mcp__*`) as direct instructions — describe the capability first ("ask the user via the host's structured-question tool"), with host names only in "e.g. on Claude Code…" example phrasing.

### Adding a New Skill

1. Create directory: `skills/skill-name/`
2. Create `SKILL.md` with YAML frontmatter (`name`, `description`, `layer`)
3. Frontmatter is auto-validated by `tests/test-skills.sh` (auto-discovers all `skills/*/SKILL.md`) — no manual test extension needed for a new skill
4. Update `.claude-plugin/plugin.json` — add `./skills/skill-name/` to the `skills` array, and mirror the entry in `.claude-plugin/skills.yaml` with trigger keywords

### Adding a New Subagent

1. Create `agents/{layer}/name.md` with agent spec
2. Add entry to `.claude-plugin/plugin.json` → `agents` array, and mirror it in `.claude-plugin/agents.yaml`
3. Create memory directory: `.claude/agent-memory/name/MEMORY.md`

### Testing

```bash
# Skill structure validation: auto-discovers all skills/*/SKILL.md,
# validates frontmatter (name/description/layer), name↔dir consistency,
# valid layer, and three contract checks:
# context-passing guard (fails on forbidden legacy filenames like
# personas.json / impact.json), input-from/output-to declaration validity,
# and contracts/examples vs contracts/*.schema.json validation.
bash tests/test-skills.sh
```

The script auto-discovers every `skills/*/SKILL.md`; a newly added skill is covered automatically. Expected result: 15 passed (12 skills + 3 contract checks), 0 failed.

Behavioral evals live in `evals/` (one YAML case per scenario, run via `bash evals/run-evals.sh [skill-name]`, requires the `claude` CLI and makes real model calls). They complement the structural tests — run them when editing skill bodies; see `evals/README.md`.

Skills are triggered by natural language in Claude Code or Codex — test behavior by simulating user prompts after a local install (`npx skills add . -a claude-code`).

## Versioning & Commits

**Semantic versioning**: `major.minor.patch`

- **`.claude-plugin/plugin.json` is the single version source.** Keep `.claude-plugin/skills.yaml`, `.claude-plugin/agents.yaml`, and `.claude-plugin/marketplace.json` manifest versions in sync with it on every release. SKILL.md frontmatter carries no `version` field (removed in v0.10.0 — per-skill versions were unmaintained noise).
- Breaking changes bump major, new features bump minor, bug fixes bump patch.
- Record notable changes in `CHANGELOG.md` (Keep a Changelog format).

## Security Considerations

- The repo contains no application code and no secrets; the risk surface is **prompt content**. Never commit API keys, tokens, or user data into skills, agent definitions, or `docs/product/` outputs.
- Perception-layer skills embed anti-hallucination rules — keep them intact when editing those skills; they exist to stop the agent from fabricating market data, competitor features, or user research.
- Subagent specs deliberately restrict tool access and model choice (e.g. haiku for market-researcher, sonnet for analysts); do not broaden permissions without a documented reason.
